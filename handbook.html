第 1 章 案例分析总论

1.1 阅卷逻辑

  • 按点给分，关键词优先。写一堆废话不如写 4 个准确术语。
  • 每个小问通常 5–8 分，一般要答 3–5 个点。
  • 计算题有过程分，公式、代入、结果、单位都要写。
  • 开放题没有标准答案，考察的是框架是否完整、是否结合题干。

1.2 四步答题法

  1. 先读问题（30 秒），知道要回答什么。
  2. 带着问题读题干，划出角色、约束、数字、异常现象。
  3. 在草稿上列点，每个点一个关键词。
  4. 正式作答：术语 + 解释 + 结合本项目。

1.3 万能句式

  • “采用……方法/架构，原因是……，在本项目中具体表现为……”
  • “从……维度看，主要包括：①……；②……；③……”
  • “该方案能解决……问题，但会带来……风险，可通过……缓解。”
  • “首先……；其次……；最后……”
  • “若……，则降级为……，以保证……”

1.4 选题与时间

  • 先扫一遍 5 道题，必答第 1 题无论难易都要做。
  • 选答优先选：有计算但会算的、架构/数据库等有把握的、题干短的。
  • 每题先写会的小问，再回头啃难的，不要在一小问上耗太久。
  • 绝不空白。开放题写通用框架也能拿基础分。

1.5 计算题通用要求

  • 先写公式，再代入数字，最后写结果和单位。
  • 关键路径题画出网络图或表格，标出 ES、EF、LS、LF。
  • 挣值题先列 PV、EV、AC，再算偏差和绩效指数。
  • 可靠性题先判断串联还是并联，再套公式。

2.2 代表例题

某互联网公司拥有 30 余个基于大模型的 Agent 应用，各团队各自维护对话上下文，存在重复建设、跨会话遗忘、token 成本高等问题。公司决定建设统一的 Agent Memory 平台，由你担任系统分析师。平台需同时支持短期记忆与长期记忆，服务业务方、Agent 开发者和终端用户三类干系人。项目启动后，需求从各业务线不断涌入，同一功能存在多种表述，变更频繁。

问题：

  1. 本项目可采用哪些需求获取方法？分别说明适用场景。（5 分）
  2. 按业务需求、用户需求、系统需求三个层次，各举一例。（6 分）
  3. 针对需求频繁变更，给出需求变更管理的主要流程。（8 分）
  4. 列出本项目的至少 4 项非功能需求，并给出可度量指标。（6 分）

2.3 参考答案

  1. 需求获取方法：
  • 访谈：面向业务负责人，获取目标与约束。
  • 问卷：面向 30 余个 Agent 团队，收集共性需求。
  • 原型：用可交互原型验证记忆检索与注入流程。
  • 观察：分析真实会话日志，发现隐性需求。
  • 文档分析：梳理现有 Agent 接口文档与数据模型。
  • JAD：多业务线集中研讨，解决需求冲突。
  • 头脑风暴：挖掘创新场景。
  1. 三个层次：
  • 业务需求：为多条业务线提供统一记忆能力，降低重复建设成本。
  • 用户需求：Agent 开发者希望通过标准 API 在半天内接入记忆能力。
  • 系统需求：支持多租户隔离，检索 P99 ≤ 200ms，租户数据互不可见。
  1. 变更流程：变更申请 → 影响分析（范围、进度、成本、质量）→ CCB 评审 → 审批 → 实施 → 验证 → 更新基线 → 通知干系人 → 归档。
  1. 非功能需求：
  • 性能：检索 P99 ≤ 200ms，写入吞吐 ≥ 2000 万条/日。
  • 可靠性：系统可用性 ≥ 99.95%。
  • 安全性：租户数据隔离，个人信息脱敏。
  • 可扩展性：向量规模支持从 1 亿扩展到 10 亿。
  • 易用性：提供 SDK 与接入文档，接入工作量 ≤ 0.5 人天。
  • 可维护性：各服务可独立部署与发布。

2.4 答题模板

  • 问方法：“采用……方法，适用于……场景，在本项目中用于……”
  • 问分类：“业务需求是……；用户需求是……；系统需求是……”
  • 问流程：“第一步……；第二步……；最后……”
  • 问指标：“……维度，指标为……，度量方式为……”

2.5 易错点

  • include 与 extend 混淆：include 是必选的公共行为，extend 是条件触发的可选行为。
  • 业务需求与用户需求混淆：业务需求是组织目标，用户需求是用户完成任务的需要。
  • CCB 不是一个人，是变更控制委员会。
  • 非功能需求只写名词不给指标，拿不到满分。

第 3 章 案例题型二：系统建模

3.1 知识地图

图形用途必背
用例图系统边界与功能参与者、用例、include、extend、泛化
类图静态结构依赖 < 关联 < 聚合 < 组合 < 泛化
顺序图对象交互时序对象、生命线、同步/异步消息、返回
状态图对象生命周期状态、事件、迁移、监护条件
活动图业务流程/并发开始、活动、判断、分叉汇合、结束
DFD数据流外部实体、加工、数据流、数据存储；父子平衡、数据守恒

聚合与组合的区别：聚合是弱整体-部分，部分可独立存在；组合是强整体-部分，生命周期一致。

3.2 代表例题

在 Agent Memory 平台的分析阶段，你需要对记忆的生命周期和检索交互进行建模。记忆条目从写入到删除经历多个状态；一次检索涉及网关、查询改写、向量检索、全文检索、重排等对象。

问题：

  1. 识别参与者并列出主要用例，说明 include 与 extend 的使用。（6 分）
  2. 给出记忆条目的状态图，写明状态、事件与迁移。（7 分）
  3. 用顺序图描述一次记忆检索的主要对象与消息。（6 分）
  4. 说明 MemoryItem 与 VectorRecord、Session 与 MemoryItem 的关系类型及理由。（6 分）

3.3 参考答案

  1. 参与者：Agent 开发者、终端用户、平台管理员、外部系统。

主要用例：写入记忆、检索记忆、生成摘要、遗忘/删除、租户管理、审计。 include：检索记忆 include 权限校验；写入记忆 include 内容审核。 extend：检索记忆 extend 重排序（条件触发）；写入记忆 extend 冲突消解（条件触发）。

  1. 状态图：
  • 状态：待生效 → 生效 → 衰减中 → 归档 → 已删除。
  • 事件：审核通过、被命中、TTL 到期、重要性低于阈值、删除请求。
  • 迁移：待生效—审核通过→生效；生效—被命中→生效（刷新访问时间）；生效—长期未命中→衰减中；衰减中—重要性低于阈值或 TTL 到期→归档；归档—删除请求或保留期结束→已删除。
  1. 顺序图对象与消息：
  • Agent → 记忆网关：发起检索请求。
  • 记忆网关 → 权限服务：校验租户与权限。
  • 记忆网关 → 查询改写服务：改写查询。
  • 查询改写服务 → 向量库 / Elasticsearch：并行召回。
  • 记忆网关 → 重排服务：合并去重并重排。
  • 重排服务 → 记忆网关：返回 Top-K。
  • 记忆网关 → Agent：返回记忆并注入提示词。
  1. 关系类型：
  • MemoryItem 与 VectorRecord 是组合关系。向量随记忆删除而删除，生命周期一致。
  • Session 与 MemoryItem 是聚合关系。会话结束后，记忆仍可作为长期记忆独立保留。

3.4 答题模板

  • 用例：“参与者包括……；用例包括……；其中…… include……，…… extend……”
  • 状态：“对象从……开始，在……事件下迁移到……，满足……条件时进入……”
  • 顺序：“……向……发送……消息，……处理后返回……”
  • 类关系：“……与……是……关系，理由是……”

3.5 易错点

  • include 箭头方向画反：被包含用例指向包含用例。
  • 状态图把“动作”当状态，状态应是对象所处的稳定状况。
  • 顺序图漏掉返回消息或生命线。
  • 聚合与组合理由说不清，记住“生命周期是否一致”。

DFD 三类错误（2024 下问 3，6 分，必背）

  • 黑洞：只有输入流、没有输出流。
  • 奇迹：只有输出流、没有输入流。
  • 灰洞：有输入也有输出，但输入不足以产生该输出。

再加四条检查项：父图与子图的数据流必须平衡；每个加工至少一进一出；每个数据存储必须有流入和流出；一条数据流至少有一端是加工。

5.6 真题补充：范式判断、SQL 与反规范化

范式判断四步法（每年数据库题都用）

  1. 写出函数依赖集，求候选键（能推出全部属性的最小属性组）。
  2. 检查属性是否原子 → 1NF。
  3. 检查非主属性对候选键是否存在部分依赖 → 有则不满足 2NF。
  4. 检查是否存在传递依赖（X→Y、Y→Z，Y 不是候选键）→ 有则不满足 3NF。
  5. 检查每个决定因素是否都是候选键 → 有一个不是就不满足 BCNF。

答题句式：“该关系的主键是……，函数依赖有……，因此满足 3NF 但不满足 BCNF，原因是……不是候选键却决定了……。”

BCNF 分解：找出违反 BCNF 的 X→A（X 不是候选键），拆成 R1(X,A) 与 R2(R−A)，再对 R1、R2 重复检查，直到每个决定因素都是候选键。例：R(员工ID, 部门ID, 部门名)，部门ID→部门名 违反 BCNF，拆成 (部门ID, 部门名) 与 (员工ID, 部门ID)。

SQL 填空（2024 上、2024 下）：SELECT 补查询列，FROM 补表名与别名，WHERE 补连接条件和业务条件。注意非等值连接，例如“员工技能水平不低于项目需求水平”写成 t3.技能水平 >= t4.需求水平。补完要检查连接条件是否覆盖所有表，否则会出现笛卡尔积。

反规范化（2024 上问 2）：为减少频繁 JOIN，把常用列冗余到一张表或建汇总表，用空间换时间。缺点是数据不一致、存储增加、更新逻辑复杂。三种补救：触发器自动维护、应用层同一事务维护、异步消息或物化视图定时刷新。答题要写“思路 + 缺点 + 解决办法”三段。

触发器（2024 上问 3）：常用于数据变更后同步冗余表，多为 AFTER 触发器。缺点：逻辑隐蔽、与 DBMS 耦合、拉长事务影响并发、难测试和版本管理。

索引与 SQL 优化：在连接列和过滤列建索引；先过滤再连接；避免在索引列上做函数运算；用覆盖索引减少回表；用执行计划确认是否走索引；小表驱动大表。

视图的作用：简化复杂查询、提供逻辑独立性、控制访问权限；性能敏感场景可用物化视图，代价是需要刷新。

6.6 真题补充：成本效益、配置与质量

成本效益计算（系统规划题常考）

  • 净现值 NPV = Σ 各年净现金流 ÷ (1+i)^n，NPV 大于 0 才值得投。
  • 投资回收期：累计净现金流由负转正的时间点。
  • ROI = 年均净收益 ÷ 总投资。
  • 答题写公式、代入、结果、结论四步，单位不能丢。

挣值补充：VAC = BAC − EAC；TCPI = (BAC−EV)÷(BAC−AC)，表示剩余工作必须达到的成本效率。

压缩工期三原则：只压关键路径上的活动；优先压赶工成本最低的；压缩后重新计算关键路径，防止出现新的关键路径。

配置管理：配置项、基线（功能基线、分配基线、产品基线）、版本控制、变更控制、配置审计。常问“为什么要建基线”——基线是变更比较和回滚的依据。

质量：质量保证关注过程（评审、审计、过程规范），质量控制关注结果（测试、检查、缺陷分析）。

风险定量：EMV = 概率 × 影响金额，用来比较不同应对方案的期望损失。

6.7 真题补充：维护与系统转换

测试内容已独立成章，见第 7 章「软件测试技术」。

系统转换方式：直接转换（成本低、风险高）、并行转换（安全、成本高）、分段转换（按模块分批）、试点转换（先小范围）。

维护四类型：改正性（修缺陷）、适应性（适应环境变化）、完善性（加功能、优化性能）、预防性（提前改造防患）。

新技术一句话：边缘计算（计算下沉到靠近数据源，降时延省带宽）、数字孪生（物理实体在数字空间的实时映射）、区块链（分布式账本、不可篡改、共识）、隐私计算（数据可用不可见）。

本章必记：关键路径算法、四个挣值公式、EAC、四种风险应对、可靠性公式、NPV、质量保证与质量控制、转换方式。（测试见第 7 章）

7.3 静态测试与动态测试（2025 下原题）

静态测试：不运行程序，检查需求、设计、代码和脚本。

  • 三类人工手段：评审、走查、审查（审查最正式）。
  • 工具化手段：静态分析，用 SonarQube、ESLint、SpotBugs，检查圈复杂度、重复代码、空指针、并发隐患。
  • 对象：需求规格、设计文档、源代码、测试脚本、用户手册。
  • 价值：缺陷发现早、修复成本低，属于测试左移。

动态测试：运行程序，用黑盒与白盒方法验证行为，覆盖单元、集成、系统、验收四个层次。

7.5 白盒覆盖（由弱到强）

语句覆盖 < 判定覆盖 < 条件覆盖 < 判定/条件覆盖 < 条件组合覆盖 < 路径覆盖。

  • 语句覆盖：每行代码至少执行一次。
  • 判定覆盖：每个判断的真假分支都走到。
  • 条件覆盖：判断里的每个条件都取真和假。
  • 路径覆盖：所有可行路径都走一遍，最强也最贵。

单元测试一般要求判定覆盖或条件覆盖，核心算法才要求路径覆盖。

7.6 测试阶段与类型

  1. 单元测试：测函数与类，开发自测，白盒为主。
  2. 集成测试：测模块间接口，策略有自顶向下、自底向上、三明治。
  3. 系统测试：验证整体功能与非功能，黑盒为主。
  4. 验收测试：业务方确认，α 在开发方场地、用户参与；β 在用户真实环境。

其他类型：冒烟测试（每次构建先跑核心）、回归测试（确认修改没破坏旧功能）、兼容性测试、安全测试、易用性测试。

V 模型：需求对应验收测试、概要设计对应系统测试、详细设计对应集成测试、编码对应单元测试。左边每做一步设计，右边就有一层测试等着。

7.7 测试管理与缺陷管理

测试管理：测试计划（范围、策略、进度、资源、风险）、用例库、测试环境与数据、准入准出标准、测试报告。

准入：冒烟通过、环境就绪、版本可测。准出：用例执行率 100%、通过率达标、遗留缺陷等级可接受——不是“测得差不多了”。

缺陷管理：新建 → 确认 → 分配 → 修复 → 验证 → 关闭；按 P0–P3 分级，P0 立即响应。度量指标：缺陷密度、缺陷逃逸率、平均修复时间、重开率。

7.8 自动化与性能测试

自动化：接口自动化优先，稳定且成本低；UI 自动化只保留核心流程；接入 CI，每次合并跑冒烟，每日跑全量回归。

性能测试五类：负载测试（逐步加压找瓶颈）、压力测试（超负荷看是否崩溃）、并发测试（多用户同时操作）、稳定性测试（长时间运行看内存与 GC）、容量测试（找最大承载）。

核心指标：TPS/QPS、响应时间（P95/P99）、错误率、资源利用率（CPU、内存、IO）。

7.9 案例答题模板

  • 问方法：“该项目采用……方法，适用于……场景，具体做法是……”
  • 问用例：“用等价类划分……，用边界值覆盖……，用判定表组合……，用场景法串联……”
  • 问阶段：“单元测试由开发完成，集成测试验证接口，系统测试验证整体，验收测试由业务方确认。”
  • 问改进：“引入自动化回归、测试左移、质量门禁、缺陷闭环管理。”

7.10 论文写法（对应论文八）

三段式：

  1. 项目背景加你负责的测试工作（测试策略、用例体系、质量门禁）。
  2. 静态与动态测试的概念、方法、工具，结合项目说明怎么用。
  3. 分层实施加自动化、性能与指标效果。

必写三个数字：缺陷逃逸率、回归时间、性能指标（如 P99）。常见失分：只背黑盒白盒名词、不写项目、不给指标。

完整范文见 论文八。

易错点

  • 把静态测试说成“不测代码”——它既查文档也查代码。

  • 验收测试写成“开发自测”。
  • 缺陷只写“修复”，不写验证与关闭。

第 8 章 论文总论

8.1 阅卷关注点

  • 切题：题目的每个子问都要在正文中有对应章节。
  • 真实：有具体项目、具体角色、具体数字、具体问题。
  • 深度：不是教科书式介绍，而是“我怎么做、为什么这么做、遇到什么问题”。
  • 结构：摘要、背景、论述、实践、效果、结尾完整。
  • 表达：字数够、字迹工整、分点清晰。

8.2 万能结构（约 2500 字）

部分字数内容
摘要300背景 + 角色 + 主题 + 方法 + 效果
一、项目背景400时间、单位、项目名、人数、周期、团队、我的职责
二、理论与方法500分点回答题目要求的概念与方法

8.3 摘要模板（填空）

“____ 年 ____ 月，我作为 ____（角色），主持了 ____（项目名称）的 ____（设计/实施/分析）。该项目投入 ____ 人、历时 ____ 个月，目标是 ____。本文以该项目为例，论述 ____（题目主题）。在项目中，我采用 ____ 方法，通过 ____ 措施，解决了 ____ 问题。系统上线后，____（量化效果）。实践表明，____（结论）。”

摘要不要写“本文首先介绍了……其次介绍了……”，要写项目、方法、效果。

8.4 正文写法

  • 背景段：用具体名词，不要“某公司”。写清业务痛点。
  • 理论段：每个子问一段，先定义再展开，控制在 150–200 字。
  • 实践段：分 3–4 个小标题，每个小标题写“做法 + 原因 + 效果”。
  • 效果段：至少 2 个量化指标，再写 2 点不足。
  • 不足要真实：多模态不支持、评测集不足、跨租户共享不完善等。

8.5 常见失分

  • 写成技术综述，没有项目和“我”。
  • 题目要求的三问只回答了一问。
  • 项目背景假大空，没有人数、周期、团队、规模。
  • 摘要与正文数据不一致。
  • 字数不足 2000，或超过 3000 太多。
  • 没有小标题，阅卷老师找不到得分点。
  • 字迹潦草、涂改多。

8.6 时间与选题

  • 10 分钟：读 4 道题，选最贴合自己项目的 1 道，列提纲。
  • 95 分钟：按提纲写，先写正文，最后写摘要。
  • 15 分钟：检查字数、子问覆盖、数据一致性、错别字。
  • 选题优先级：架构设计 > 测试 > AI/RAG > 需求工程 > 可靠性 > 数据 > 安全 > 建模 > 项目管理。

本章必记：300 字摘要、五段结构、三个子问都要答、量化效果、两点不足。

9.2 背景段（可直接背，约 330 字）

2025 年 10 月，我所在的公司启动了智能助手统一记忆平台（Agent Memory）项目，我担任项目负责人兼系统分析师。该项目投入 18 人、建设周期 9 个月，目标是解决各业务线 Agent 重复建设记忆能力、上下文窗口受限、长期记忆缺失等问题。平台需为 30 余个 Agent 应用提供统一的短期记忆与长期记忆服务，日均记忆写入约 2000 万条，检索峰值 3000 QPS。团队共 18 人，包括产品 2 人、算法 4 人、后端 7 人、前端 2 人、测试 2 人、运维 1 人。我负责总体需求分析、架构设计、技术选型、迭代计划与跨团队协调。平台采用分层、微服务与事件驱动架构，基于 Kubernetes 部署，核心存储包括 MySQL、Redis、Milvus、Elasticsearch 与对象存储。2026 年 6 月系统通过验收并上线，检索 P99 由 850ms 降至 180ms，回答准确率提升 23%，token 成本下降 35%，可用性达到 99.95%。

9.3 系统架构

  • 接入层：记忆网关，统一鉴权、限流、路由。
  • 服务层：记忆写入、记忆检索、摘要、生命周期、租户权限、记忆网关六个微服务。
  • 存储层：MySQL、Redis、Milvus、Elasticsearch、对象存储。
  • 异步链路：Kafka 承接写入事件，削峰解耦。
  • 部署：Kubernetes 多可用区，服务独立扩容。

9.4 短期记忆（会话内）

  • token 预算：系统提示、长期记忆注入、最近对话、当前输入按比例分配。
  • 滑动窗口：保留最近 N 轮对话。
  • 分层摘要：超预算时先做逐轮摘要，再做会话摘要。
  • 关键信息抽取：实体、意图、用户偏好、待办事项。
  • 指代消解：把“它、那个”还原为具体对象，保证多轮连贯。

9.5 长期记忆（跨会话）

  • 写入流水线：抽取事实/偏好/事件 → 规范化 → 去重 → 重要性评分 → 向量化 → 入库。
  • 记忆类型：事实记忆、情景记忆、程序记忆、工作记忆。
  • 检索流程：查询改写 → 向量 + BM25 混合召回 → 租户/时间/权限过滤 → 重排 → Top-K 注入提示词。
  • 遗忘机制：TTL、重要性衰减、访问频次、容量上限。
  • 冲突消解：版本号、来源权重、置信度、时间优先、人工复核。

9.6 数据与存储

  • MySQL：记忆元数据、租户、权限、审计。
  • Redis：会话短期记忆、热点缓存、限流。
  • Milvus：向量索引，HNSW。
  • Elasticsearch：全文检索、BM25、日志。
  • Kafka：异步写入与削峰。
  • 对象存储：原文、冷数据归档。
  • 冷热分离：30 天内热数据留在高性能存储，冷数据下沉。

9.7 安全与可靠性

  • 安全：OAuth2 + JWT、RBAC + ABAC、租户 namespace 隔离、TLS1.3、AES-256、KMS、PII 脱敏、审计日志、记忆投毒防护。
  • 可靠性：多副本、多可用区、熔断限流、三级降级（向量检索→关键词检索→最近记忆）、灰度发布、混沌演练。
  • 指标：可用性 99.95%，MTTR 由 45 分钟降至 12 分钟。

9.8 两个技术难点（论文“踩坑”素材）

难点一：短期与长期记忆的 token 预算冲突。 初期把大量长期记忆注入提示词，导致延迟升高、成本上升，且关键上下文被挤掉。解决方法是动态预算：先按请求类型分配固定比例，再用重排分数决定注入条数，超预算时对记忆做摘要压缩，并优先保留最近对话与高置信度记忆。优化后 P99 下降，token 成本下降 35%。

难点二：多来源记忆冲突与记忆投毒。 不同 Agent 写入同一用户的偏好，出现新旧记忆矛盾；低可信来源的脏数据会污染后续回答。解决方法是引入版本号与来源权重，写入时做语义去重与冲突检测，冲突时保留版本并按置信度排序，低可信来源进入人工复核；检索时优先高置信度、近期记忆。上线后记忆准确率明显提升，错误扩散得到控制。

9.9 不足与改进

  • 多模态记忆尚未支持，图片、语音、视频中的信息无法统一检索。
  • 跨租户知识共享机制不完善，公共知识重复建设。
  • 离线评测集覆盖不足，长尾场景效果不稳定。
  • 改进：引入多模态向量、联邦检索、扩充评测集与线上反馈闭环。

9.10 可复用亮点清单

  1. 短期 + 长期双层记忆架构。
  2. token 预算动态分配。
  3. 分层摘要压缩。

17.4 摘要范文

2025 年 10 月，我作为项目负责人兼系统分析师，主持了公司智能助手统一记忆平台的建设。项目面临模型效果不确定、向量库性能不足、数据合规、关键人员依赖与需求蔓延等风险。本文以该项目为例，论述项目风险管理。我组织团队采用头脑风暴与检查表识别出 18 项风险，使用概率与影响矩阵排序，并制定应对计划：对模型效果风险采用 POC 与灰度发布减轻；对向量库风险采用双引擎与备选方案转移；对合规风险采用数据最小化、脱敏与合规评审规避；对关键人员风险建立 AB 角与文档沉淀；对需求蔓延建立变更控制与迭代评审。通过双周风险复盘与触发器监控，项目按期上线，未发生重大风险事件。

17.5 正文示范段

我们用概率与影响矩阵对风险排序，把模型效果不达标、向量库性能不足、数据合规列为首要风险。对模型效果风险，先做 POC 验证，再小流量灰度，失败可快速回滚；对向量库风险，准备双引擎与降级方案；对合规风险，提前做数据映射、脱敏与合规评审。

风险监控采用双周复盘与触发器机制：一旦灰度指标低于阈值、写入延迟超过阈值或出现合规告警，就启动预定应对流程。每个风险都指定责任人与关闭标准，避免风险清单停留在纸面。

17.6 本题高分句

风险管理的目标，是让风险在变成问题之前被看见。
